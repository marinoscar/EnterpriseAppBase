## 6. threat model of the GUC approach
PASS  ANY SQL executed on a connection can set the GUC (including to another org, or the bypass flag): RLS here defends against missing or wrong scoping in app code, NOT against SQL injection or arbitrary raw SQL
  consequence: unscoped raw SQL needs a lint rule (spec: "Lint"), and the bypass flag may only be set by the system client wrapper.

## 7. foreign keys and RLS: referential-integrity checks BYPASS row-level security
PASS  a plain FK lets org B store a reference to org A's parent (the FK check reads the parent as the table owner, ignoring RLS)
PASS  ...while org B cannot read that parent: a dangling-looking cross-tenant reference (and an existence oracle for foreign ids)
PASS  a COMPOSITE foreign key (parent id, org id), declared in Prisma with fields: [nodeId, orgId], refuses the cross-org reference  (Foreign key constraint violated on the constraint: `spike_leaves_node_id_org_id_fkey`)
PASS  and the same-org reference works

## 8. the three bypass options

### Option B: ENABLE without FORCE; the owner bypasses; scoped transactions SET LOCAL ROLE
PASS  B: UNSCOPED code (no SET LOCAL ROLE) sees EVERY org's rows: it FAILS OPEN  (n=12)
PASS  B: inside SET LOCAL ROLE + set_config the scope is enforced (5 rows)
PASS  B: the tenant role with no org set sees nothing (the tenant role itself is fail-closed)
   B costs: every new table needs GRANT ... TO tenant role (a package migration obligation), a second role on every deployment, and a role switch per transaction;
   B can never FORCE (the owner would then be subject to policies and the "system" path disappears), so protection depends on every request path remembering SET LOCAL ROLE.
PASS  B: pg_dump as the owner works with the current default arguments (owner bypasses) and captures all rows

### Option C: a separate login role with BYPASSRLS
PASS  C: a BYPASSRLS login sees every row of a FORCEd table with no flag at all  (n=40)
PASS  C: pg_dump as that role works with today's default arguments (row_security off is fine for a BYPASSRLS role)
--- a CREATEROLE (non-superuser) role like app_job_minter tries CREATE ROLE ... BYPASSRLS
    permission denied to create role
PASS  C: a CREATEROLE role cannot mint a BYPASSRLS role, so the per-job dump role (pg-job-role.broker.ts) cannot be made to bypass RLS this way  (permission denied to create role)
PASS  C: nor can it ALTER an existing role to BYPASSRLS  (permission denied to alter role)
   C also adds a second DATABASE login and therefore a new deployment secret (and one more thing to rotate and to hold outside the encrypted `credentials` table).
   RDS: whether the master user may CREATE ROLE ... BYPASSRLS / hold BYPASSRLS is UNMEASURED here; the manual check is in docs/runbooks/rds-proxy-rls-check.md.
