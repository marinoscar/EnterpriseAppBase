`deploy install` provisions a dedicated, least-privilege application database role instead of running the API as the operator's login (#980). Row-level security is skipped for a superuser or a `BYPASSRLS` role, so an API that connected as the administrator the operator typed served every organization's rows to every other. Install's `environment` step now calls `ensureApplicationRole` (`engine/deploy/app-role.ts`, the one implementation, shared with update): a privileged login is used once, in memory, to create `<app>_app` (`LOGIN NOSUPERUSER NOBYPASSRLS CREATEDB CREATEROLE`, `createrole_self_grant = 'inherit, set'`) with a generated 32-byte password sent as a SCRAM-SHA-256 verifier on `psql`'s stdin (new `runPsqlScript`; `runCommand` gains `input`), and only the role is written to `.env` (0600). An existing database is re-owned with `ALTER ... OWNER TO` in one transaction (never `REASSIGN OWNED BY`), after a backup recommendation and consent. New required check `database-role-ordinary` gates `validate-environment`, the `ensure-database` re-verify and `deploy doctor`. New flags on `install` and `update`: `--app-db-user`, `--admin-user` (password only from `<PREFIX>DB_ADMIN_PASSWORD` or the answers key `DB_ADMIN_PASSWORD`, never a flag), `--skip-role-provisioning`, `--allow-superuser` (recorded in the deploy state as `allowSuperuser` with the `allowSuperuserLogin` it applies to), `--rotate-app-password`, `--provision-app-role`, `--transfer-ownership`, `--allow-reduced-role`, `--show-credentials`; the answers keys `DB_ADMIN_USER`, `DB_ADMIN_PASSWORD` and `APP_DB_USER` are removed from the answers and never reach `.env`. `deploy update` gains a `database-role` step (added to `UPDATE_STEP_IDS` between `environment-drift` and `ensure-database`) that warns on a superuser `POSTGRES_USER` and, with consent, migrates the deployment onto a dedicated role and restarts the API. An existing role is never taken over: if it exists and the recorded credentials do not open it, install refuses unless `--rotate-app-password` (or an interactive yes naming the role); the password is set last, after `.env` holds it, and `.env` is put back if the server refuses it. Behaviour change: an install whose entered login is privileged and that gives no consent (a non-interactive run without `--provision-app-role`, `--skip-role-provisioning` or `--allow-superuser`) now stops instead of deploying as the superuser. `.env.example` and the environment variable set are unchanged.
