Date operations follow the user's `profile.timezone`, and emails render in the recipient's zone. Contract: new subpath `@marinoscar/platform-contract/timezone` with the pure, DST-correct zone math the API and the web share (`getTimeZoneOffsetMinutes`, `getZonedParts`, `zonedDateKey`, `zonedDayStart`, `addCalendarInZone`, `addDaysToDateKey`, `isDateKey`), `DEFAULT_SERVER_TIME_ZONE` (`'UTC'`) and `TIME_ZONE_HEADER` (`'x-time-zone'`); `readProfileTimeZone(settingsValue)` in `/settings`. API zone resolution: `SettingsResolver.resolveUserTimeZone(userId)` and `resolveRequestTimeZone(request, userId?)` (stored profile zone, then a valid `X-Time-Zone` header from a client on "Automatic", then UTC), also bound as `REQUEST_TIME_ZONE_RESOLVER` in `@marinoscar/platform-api/core` (with `readRequestTimeZoneHeader`, `chooseTimeZone`, `resolveRequestTimeZoneWith`) so slices below settings can use it `@Optional()`. Emails: `EmailRenderContext.timeZone`, `formatEmailDateTime` and `formatEmailDate` (the zone's short name always printed, plus the UTC time outside UTC, e.g. `Oct 26, 2026, 9:42 PM CDT (Oct 27, 02:42 UTC)`); every platform template that shows a time uses them (test-email, role-changed, job-failed, node-offline, backup-failed, restore-completed). The sharing templates take optional `formatDate`/`formatDateTime` in the kit (UTC, labelled, without them) and `SharingNotifier` calls take an optional `SharingNotifyHint { actorUserId }`. Notifications: `NotificationRecipient.timeZone` is read with the recipient and flows to the email channel (per-recipient render context) and to the bell and push renderers (`BrowserNotificationTemplate` is `(data, ctx?: { timeZone? })`); `NotifyOptions.timeZone` is a render hint for a recipient with no zone. The email and push test sends use the requester's zone. AI usage: the three reports take an optional `tz` (default profile zone, then `X-Time-Zone`, then UTC), cut days with a bound `AT TIME ZONE`, use local midnights for `from`/`to`, zero-fill by calendar day and echo `timeZone`. AI daily limits stay UTC midnight (quota-abuse reason); the `AI_RATE_LIMITED` details gain `resetsAt` (ISO). Exports: `ExportContext.timeZone` (required; captured at enqueue into the job payload from the request's zone), the default file name uses the zone's day, and `zonedDayStart`/`zonedDateKey` are re-exported from `/exports`. PAT: `days` and `months` lifetimes are calendar arithmetic in the requester's zone (`computePatExpiry`; month ends clamp). Behaviour change: platform emails and bell text that showed ISO timestamps now show `Mon D, YYYY, h:mm AM UTC` for a recipient without a stored zone. Back-compat: the new request header and query parameter are optional; a custom `ExportContext` builder (tests) must add `timeZone`.
