`deploy update` no longer starts a second stack when the deploy folder holds containers of two compose projects. A folder with the live stack under an app-named project (for example `kvox-nginx-1` on the bind port) and leftover containers of the legacy `compose` project was read as ambiguous and kept `compose`, so `docker compose -p compose up -d` built a parallel stack that died on `Bind for 127.0.0.1:3535 failed: port is already allocated`. The project is now picked by the strongest evidence among the containers started from the deploy folder: the project whose container publishes the bind port (running containers first), then the only project with a running container, then the only project, and is recorded in `.appctl-deploy.json` when the state has none or the legacy `compose`. When nothing separates the projects the record is kept and a warning names the projects and the state file; a recorded project is never overwritten, but a warning is printed when another project holds the bind port. `install --resume` and `--reinstall` reconcile the same way before their first compose or check call. `detectComposeProject` takes an optional `{ bindPort }` and a `found` result carries the `basis` that decided it (`bind-port`, `running` or `only`).

New required check `bind-port-owner` (the `update` and `install` preflight, and `doctor`): any container in any state that publishes the bind port under a compose project other than the one the run would use fails the run before anything is built, naming both projects, the `composeProject` fix in the state file and the exact `docker ps -aq ... | xargs -r docker rm -f` command for leftovers; a port promised to an unrelated container points to `--port`. New recommended check `stray-compose-stack` warns in `doctor` about containers of another project started from the deploy folder, with the same removal command. A stopped leftover of the deploy folder is only a warning (printed during `update`, with the removal command) when a running container of the run's own project holds the port; a running foreign container, or a stopped one with no live own holder, still fails. Neither check removes anything. The `update` preflight failure now prints each failed check's remedy, as `install` does. Apps that carry their own copy of a "port promised to another project" check can drop it.
