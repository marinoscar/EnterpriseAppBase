`deploy update`, `status` and `doctor` (and the TUI doctor) now ask Docker which compose project a deployment's containers run under when the state records none, or only the legacy `compose`, and record it. A deployment installed with an app-named project (`myapp-nginx-1`) was read as `compose`: the app's port check refused its own nginx, and every `docker compose -p compose` call would have started a second stack on the bind port. The project is the `com.docker.compose.project` label of containers whose `com.docker.compose.project.working_dir` is inside the deploy root. A recorded non-legacy project is never overwritten and Docker is not asked; the previous state file is kept once as `.appctl-deploy.json.bak`; an ambiguous answer writes nothing and warns; Docker being unavailable changes nothing. A failed `install` attempt no longer writes the assumed `compose` into the state as if it were a record. New on `@marinoscar/platform-cli/deploy`: `detectComposeProject`, `isPathUnder` and the types `ComposeProjectDetection` and `ComposeProjectCommandRunner`, so an app's own check can use the same ground truth instead of carrying a copy.
