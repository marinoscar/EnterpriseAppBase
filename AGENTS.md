# AGENTS.md

Shared rules for AI assistants working on this codebase (loaded by OpenCode, and by Claude Code through `CLAUDE.md`). Area rules live in nested `AGENTS.md` files: `apps/api`, `apps/web`, `packages/platform-api`, `packages/platform-db`. How the tools share files: [docs/AI-ASSISTANTS.md](docs/AI-ASSISTANTS.md).

## Project overview

This repository is a template: teams fork it to get a production-grade foundation for an enterprise web app.
Stack: React 19 + MUI (web), NestJS 11 on Fastify + Prisma 7 + Zod (API), PostgreSQL 16, Commander + ink (`appctl` CLI), Nginx same-origin, OpenTelemetry + Pino, Docker Compose, Node 24.
Start at [README.md](README.md) and [docs/README.md](docs/README.md) (index, with a "Doc map by task").

## MANDATORY: No real people, companies or user material

- **Material a user shares is never reused.** Never use the content of documents, notes, transcripts, screenshots or any other material the user shares with an assistant, or anything derived from it (names, numbers, quotes, structure that identifies it), in code, tests, fixtures, evaluation sets, prompts, documentation, examples, issues, pull requests or commit messages. Shared material is used only to diagnose the problem in the conversation.
- **No real names as examples.** Never use the name of a real person, or a real company, organization, product or brand, as an example anywhere in the repository: code comments, prompts, test data, fixtures, evaluation scenarios, docs, issue and PR text. Use clearly invented placeholders: `Person A`, `Avery Example`, `Org Alpha`, `Org Beta`, `Product X`, `Project P1`, and `@example.test` email addresses. Do not borrow well-known fictional brands either (Contoso, Acme, Northwind, Initech).
- **Exempt, and only these:** a real vendor or service a feature integrates by name (for example a provider adapter calling that vendor's API, its SDK package names, its documented endpoints), and legal or authorship metadata (package `author`, copyright lines, code-signing publisher name).
- **Fix what you find.** When you find a real name used as an example, replace it with a placeholder in the same change, or open a follow-up if it changes recorded snapshots.

## MANDATORY: Issue-Driven Development

Every feature and bug fix is tracked by a GitHub issue, filed **before** implementation planning is finalized (features) or the fix starts (bugs), and before any worktree or branch is created. `gh issue create` inside the repo infers the repository.

- **New feature**: `gh issue create --template feature_request.yml` (real problem, solution, component, priority, not placeholders). **Larger initiative**: `--template epic.yml`; children reference the epic.
- **Bug fix**: `--template bug_report.yml` (reproduction, expected vs. actual, component, logs).
- **Platform gap seen from an app**: `--template seam_request.yml` instead of editing platform code.
- Link the work with `Fixes #<n>` / `Relates to #<n>` in commits and the PR. Feature and bug work only; `chore`/`docs`/`refactor` need no issue.

## MANDATORY: Worktree-Based Feature Development

The main checkout stays on `main`. Every feature or fix is developed in a Git worktree.

- Worktrees live under `worktrees/<short-name>` (git-ignored); branches `<type>/<short-name>`. The **main agent** creates them after the issue exists: `git worktree add worktrees/<short-name> -b <type>/<short-name>`.
- All development and commits happen inside the worktree. To finish: commit, then `git worktree remove worktrees/<short-name>`; the branch remains for the PR.
- Never work on a feature in the main checkout. One worktree per branch; reuse an existing one.
- **Exception**: when the environment has already put you on a designated branch, work there.
- Do not open PRs unless asked.

## MANDATORY: Commit rules

- **Commit early, commit often**: small, coherent, one intent. No unrelated refactors, repo-wide formatting or dependency upgrades.
- **A behaviour change carries its tests** in the same commit or the next one.
- **Format** (Conventional Commits): `<type>(<scope>): <short imperative summary>`.
- Types: `feat`, `fix`, `refactor` (no behaviour change), `test`, `docs`, `chore`.
- Scopes: `api` `web` `cli` `db` `infra` `auth` `ai` `jobs` `nodes` `storage` `notifications` `ui` `core` `docs` `tests`.
- **Sequence**: `git status`, `git diff`, stage intentionally, `git commit`, `git status`.
- **Tests not run**: still commit, and say so in the body (`Notes: tests not run (DB env not available).`).

## MANDATORY: Settings UI Pattern

Every settings surface, admin or per-user, is a **registry-driven hub**. Detail: [docs/specs/settings-ui.md](docs/specs/settings-ui.md); web specifics in `apps/web/AGENTS.md`.

1. **Every new settings page is declared in a section registry.** Admin cards: `apps/web/src/config/adminSections.tsx` (`ADMIN_SECTIONS`); per-user cards: `apps/web/src/config/userSettingsSections.tsx` (`USER_SETTINGS_SECTIONS`). A route without a registry entry is unacceptable. Append new cards; do not insert between existing ones.
2. **A settings page is never added as a new tab on an existing settings page.** Tabs are legitimate only inside one destination for genuinely **parallel** content (example: `packages/platform-web/src/identity/ui/users/UsersPage.tsx`, Users and Allowlist). A destination gate is about reachability; a tab gate is about content.
3. **The card's `permission` is the exact string the API controller enforces**, never invented:
   - `system_settings:read` / `:write` → `settings/system-settings/system-settings.controller.ts`
   - `users:read` → `identity/users/users.controller.ts`; `allowlist:read` → `identity/allowlist/allowlist.controller.ts` (gates content inside the Users page, not the route)
   - `org_members:read` → `identity/organizations/org-members.controller.ts` (org permission via `org_admin`; `Organization` card, `feature: 'orgs'`); `org_invites:read` (`org-invites.controller.ts`) gates the Invites tab
   - `organizations:read` → `identity/organizations/organizations-admin.controller.ts` (system permission; `Organizations` card, `feature: 'orgs'`)
   - `org_settings:read` → `settings/org-settings.controller.ts` (org permission; `Organization settings` card, `feature: 'orgs'`); `org_settings:write` gates the controls
   (all under `packages/platform-api/src/`)
   Identity cards ship as data (`identityAdminSections`, `identityUserSettingsSections` of `@marinoscar/platform-web/identity/ui`); the app's registries spread them. Writes are gated inside the page, not by a second card permission.
4. **Reuse `SettingsHub` from `@marinoscar/platform-web/settings/ui`** (`packages/platform-web/src/settings/ui/SettingsHub.tsx`). Never fork it. `/settings` (`apps/web/src/pages/UserSettingsHubPage.tsx`) is a binding over the same component `/admin/settings` uses.
5. **The five coupled breakpoint gates move together or not at all** ([spec](docs/specs/settings-ui.md#breakpoint-gates)); all live in `packages/platform-web/src/`:
   1. `ShellLayout`'s `showRail` (`up('sm')`), `shell/ui/ShellLayout.tsx`
   2. `ShellBottomNav`'s own `down('sm')` self-gate, `shell/ui/ShellBottomNav.tsx`
   3. `<main>`'s `pb: { xs: 10, sm: 3 }` in `shell/ui/ShellLayout.tsx`
   4. `SettingsHub`'s `isCompactWindow` (`down('sm')`), `settings/ui/SettingsHub.tsx`
   5. `ShellAppBar`'s `isCompactWindow` (`down('sm')`), `shell/ui/ShellAppBar.tsx`

   The boundary is `sm` (600px), never `md` (900px). No shared constant binds them, deliberately.

## MANDATORY: Every Long-Running Activity Is a Queue Job

Design: [docs/specs/job-queue.md](docs/specs/job-queue.md#all-long-running-work-is-a-job).

1. **No long-running work outside the queue.** Anything that outlives the HTTP request or cron tick that started it is a registered `JobHandler` with a declared `type`, enqueued through `JobsService`. A detached `void this.doX()`, an `@OnEvent` body that downloads or spawns, and a `@Cron` body that works inline are violations. A `@Cron` only decides whether work is due and enqueues it: reference `packages/platform-api/src/jobs/tasks/job-history-purge.task.ts`, helper `enqueueHousekeepingJob` (`packages/platform-api/src/jobs/housekeeping.enqueue.ts`, exported by `@marinoscar/platform-api/jobs`).
   - Exactly three permanent exemptions: `jobs/tasks/job-stuck-reset.task.ts` (lease reaper), `jobs/tasks/temp-file-janitor.task.ts` (local disk sweep), `nodes/tasks/node-secret-sweep.task.ts` (revokes credentials brokered to nodes), all under `packages/platform-api/src/`.
   - Executable form: `apps/api/test/conformance.spec.ts` runs suites `cron-enqueue-only` and `on-event-no-io` (scan roots: `apps/api/test/jobs/cron-source-roots.ts`). A fourth exemption requires editing both the spec and the suite.
2. **Node eligibility is the default posture.** A new job type SHOULD carry `nodeResultSchema` + `persistNodeResult` unless it cannot (writes as it goes, reads several tables mid-computation, needs a privilege a remote machine must never hold; database restore is server-only). Eligibility is **derived** from those two members; there is no `nodeEligible` flag (`packages/platform-api/src/jobs/job-handler.interface.ts`). A deployment declines offload with a system setting read at claim time (`NodeOffloadService.offeredTypes()`), never by editing the handler.
3. **A node never persists a job-scoped credential.** Every per-job secret is issued through `POST /api/nodes/:id/jobs/:jobId/secret`, gated by `assertJobHeldByNode`, bounded by the job's lease, held in node memory only, revoked when the job settles or by the sweep. `job_node_secrets` stores the credential's **handle**, never material. A handler declares the need by carrying a `nodeSecretBroker` (`packages/platform-api/src/jobs/job-secret-broker.ts`). The node's own `nod_` identity token is the single exception.
4. **A job type declares its execution profile or takes the global default.** `JobHandler.profile` is optional and carries exactly `{ maxRuntimeMs, maxAttempts }` (`packages/platform-api/src/jobs/job-execution-profile.ts`). Lease, renewal interval and reaper patience derive from `maxRuntimeMs`. Never add `leaseMs` or `heartbeatMs`.
5. **Jobs carry their organization; `jobs` has no row-level security.** `EnqueueJobInput.orgId` is stored on `jobs.org_id` (`null` for a system job; housekeeping always passes `null`) and is the `org.id` span attribute, never a metric label. An org-scoped job without a natural subject uses `subjectType: 'organization', subjectId: orgId`. A handler touching org tables runs under `JobScope.run(job, fn)`.

## MANDATORY: AI Platform Rules

Design: [docs/specs/ai-platform.md](docs/specs/ai-platform.md). Recipe: [packages/platform-api/src/ai/README.md](packages/platform-api/src/ai/README.md). Operators: [docs/runbooks/ai-configuration.md](docs/runbooks/ai-configuration.md).

1. **Never import a provider SDK outside `packages/platform-ai-providers/src/<provider>/` (the lean package `@marinoscar/platform-ai-providers`; `platform-api/src/ai/providers/<provider>/` holds only Nest subclasses), or outside a provider folder an app declares to the `ai-no-sdk-leak` suite (`providerDirs`) for a provider it registered with `registerAiProvider`.** The app configures AI once (`apps/api/src/platform/ai/ai.config.ts`). A feature imports `AiModule`, injects `AiService` and calls `AiService.forUser(userId, { orgId, feature })`, never an SDK client. A new provider's SDK gets its own boundary spec.
2. **Never call AI from the browser; keys never leave the server.** Every provider call is server-side, under a key `AiKeyResolver` resolved for that call (user BYOK, organization, or deployment key), held only between resolution and the adapter call. No route, log line, span, `AiError`, `ai_usage_events` row or `ai_runs.request` row carries key material. The one exception: a realtime session's **ephemeral** provider secret, returned only by `POST /api/ai/realtime/sessions`.
3. **AI jobs are server-only, permanently.** Every `ai.*` job type implements neither `nodeResultSchema` nor `persistNodeResult`: keys are never brokered to a worker node.
4. **Route guards.** Every consumer route under `/api/ai/*` sits behind `AiEnabledGuard` plus `ai:use`, except `GET /api/ai/config` (open). Every admin route under `/api/admin/ai/*` requires `ai_config:read`/`ai_config:write` (the organization's `/api/admin/ai/org-*` routes require `org_ai_config:read`/`org_ai_config:write`) and is deliberately **not** behind `AiEnabledGuard`, so an administrator can always turn AI back on.
5. **New AI settings cards follow the Settings UI Pattern and declare `feature: 'ai'`**, so they are hidden while AI is off. The one exception is the admin `AI` card (`/admin/settings/ai`), which switches AI on and carries no `feature`.

Guardrails: conformance suites `ai-kill-switch`, `ai-rbac-matrix`, `ai-secret-egress`, `ai-key-policy`, `ai-jobs-server-only`, `ai-no-sdk-leak`, `ai-orchestration-boundary` and web suite `settings-ai-cards` discover routes, job types and cards automatically; an opt-out needs a written reason.

## MANDATORY: Invariants that are easy to break

Each is enforced by tests.

- **Raw-SQL partial unique indexes are intentional schema drift.** `jobs_active_dedup_uniq_idx`, `database_backup_runs_active_uniq_idx`, `organizations_default_uniq_idx`, `group_invites_pending_uniq_idx`, `grants_active_user_uniq_idx`, `grants_active_group_uniq_idx`, `grants_active_ref_uniq_idx`, `android_app_releases_one_current_uniq_idx` (plus non-unique `jobs_attempts_gt1_idx`, `jobs_succeeded_duration_idx`) exist only in migration SQL. Never "fix" them with `@@unique` or a `findFirst` pre-check. They are listed in `packages/platform-db/raw-sql-indexes.json`; `assertRawSqlIndexes` (`runDbConformance()`) fails on an unlisted partial or expression index; `platform db drift` checks `pg_indexes`.
- **`apps/api/prisma/schema/` is generated; never hand-edit it.** Edit the owning fragment (`packages/platform-db/schema/<slice>.prisma` or `apps/api/prisma/fragments/`), run `npm run db:compose --workspace=api`, then `prisma:generate`; CI's `db:compose:check` fails on a stale file. A back-relation on a platform model is an `extend model` block, never an edit to a platform file.
- **Row-level security is transaction-local, and the API is never a superuser.** The `org` tables (`storage_objects`, `storage_object_chunks`, `ai_runs`, `ai_usage_events`, `groups`, `group_members`, `group_invites`, `grants`, `org_settings`, `org_credentials`) force RLS on `org_id`. `app.org_id`, `app.user_id`, `app.rls_bypass` are written only with `set_config(name, value, true)` as the first statement of a transaction (`PrismaService.forOrg` / `runInOrg`, `PrismaSystemService.asSystem` / `runAsSystem`); **never a session-level `SET`**. Never use a `forOrg` client inside `$transaction(async tx => ...)` (use `runInOrg`). A job touching an `org` table carries `orgId` in its payload (without one it runs in the default org in `single` mode, fails in `multi`). Only files in `ALLOWLIST` of `apps/api/test/tenancy/system-injection-boundary.spec.ts` may inject `PrismaSystemService`, each acquisition naming a registered `SystemAccessReason`. A link between two org-owned tables is a composite foreign key including `org_id`. A migration touching an `org` table runs as `BEGIN; SELECT set_config('app.rls_bypass','on',true); ...; COMMIT;`. `RLS_POLICIES` (`packages/platform-db/rls-policies.json`) is intentional drift. RLS is inert for a superuser or `BYPASSRLS` role, so `POSTGRES_USER` must be an ordinary role owning the tables (Doctor check `db.rls_role`). See [SECURITY-ARCHITECTURE.md §18](docs/SECURITY-ARCHITECTURE.md#18-tenant-isolation-rls).
- **Every dump and restore carries BOTH `--enable-row-security` and `PGOPTIONS=-c app.rls_bypass=on`.** The flag alone exits 0 with an empty-table archive; the option alone is refused. `buildPgDumpArgs`, `buildPgRestoreArgs` (`packages/platform-api/src/db-backup/`), the guided manual-restore block and the CLI node-side dump (`packages/platform-cli/src/engine/node/pg-dump.ts`) all do; the option goes in the environment, never argv; the connection must be direct (no transaction-mode pooler). Proof: `apps/api/test/db-backup/db-backup-rls.db.spec.ts`; [database-backup.md](docs/specs/database-backup.md#row-level-security).
- **A backup archive is never buffered**: `pg_dump` streams into object storage; the upload and the dump's exit code are both awaited.
- **No restore pre-flight may create, drop or rename anything**; the cluster admin connection lives outside the Prisma pool, on the `postgres` database ([database-restore.md](docs/specs/database-restore.md)).
- **`notify()` runs after the triggering write commits, outside any `$transaction`** ([notifications README](packages/platform-api/src/notifications/README.md)).
- **An installed migration is never edited; `platform.lock` proves it.** Platform migrations live in `packages/platform-db/migrations` (the base's 22, `0001_initial` to `0022_add_retention_created_at_indexes`); `apps/api/prisma/migrations/**` holds installed copies under their original names (never rename one). `prisma/platform.lock` records each sha256 and `npm run db:check` fails on any byte change in either copy. **Comments inside `migration.sql` count**, so any comment clean-up must exclude `**/migration.sql`. See [DEVELOPMENT.md](docs/DEVELOPMENT.md#authoring-a-platform-migration).
- **A job `type` string is permanent** once jobs of that type exist; `apps/api/test/jobs/job-type-snapshot.spec.ts` pins every registered type.

## Architecture principles

1. **Separation of concerns**: the UI handles presentation only; the API handles all business logic and authorization.
2. **Same-origin hosting**: UI at `/`, API at `/api`, API reference (Scalar) at `/api/docs`.
3. **Security by default**: every endpoint declares `@Auth()` unless deliberately public. There is no global JWT guard (the platform's only `APP_GUARD` is `MaintenanceGuard`, first; an app may add a global guard such as a throttler only by listing it with a reason in the `host` conformance suite's `allowedAppGuards`), so a route without `@Auth()` is public.
4. **API-first**: all business logic lives in the API layer.

## Security guidelines

- Deployment secrets come from environment variables (`infra/compose/.env.example`), never from code.
- Storage, AI, Web Push (VAPID) and SMTP are configured at runtime in the admin UI and must **never** get environment variables (no `STORAGE_PROVIDER`, `S3_BUCKET`, `S3_REGION`, `S3_ENDPOINT`, `OPENAI_API_KEY` or equivalent). Two sources of truth is the failure this prevents.
- The telemetry store connection is runtime-configured at `/admin/settings/telemetry`; `GREPTIME_*` is only the deployment default ([telemetry.md §8](docs/specs/telemetry.md#8-runtime-connection)).
- Runtime-configured credentials are encrypted with `SECRETS_ENCRYPTION_KEY` before storage.
- The access JWT (15 minutes) is read only from `Authorization: Bearer`. The only cookie is the HttpOnly `refresh_token`, rotated on use.
- Validate input on every endpoint (Zod). Profile-image uploads: images only, size and type limits.
- The email allowlist restricts access; `INITIAL_ADMIN_EMAIL` bypasses it.

## Environment variables

- [`infra/compose/.env.example`](infra/compose/.env.example) is the reference; do not duplicate it.
- `DATABASE_URL` is built at runtime from `POSTGRES_*`: use `npm run prisma:*`, never bare `npx prisma`.
- Never add an environment variable for runtime-configured features.
- `.env.example` is generated: a platform variable goes in `packages/platform-infra/env/base.env.example`, an app variable in `infra/compose/app.env.example`, then `npm run platform:infra:sync`.
- **Never add a commented `# KEY=value` line to `.env.example`**: the CLI's `parseEnvExample` reads it as a declared variable and fails the env-spec test. Document `MAINTENANCE_MODE` values as prose; the file already has exactly one commented default for it.

npm run test:run --workspace=web            # also cli; typecheck: npm run typecheck --workspace=<api|web|cli>

## Subagents

Delegate development work to the matching agent in the tool's agents folder: `.opencode/agents/` for OpenCode, `.claude/agents/` for Claude Code. Agents: `backend-dev` (API), `frontend-dev` (React, MUI), `database-dev` (schema, migrations), `testing-dev` (tests), `docs-dev` (docs), `ops-dev` (container rebuilds, migrations, typecheck). Multi-domain work runs them in sequence (database, backend, frontend, testing, docs). Do not write controllers, services, components, Prisma schema, migrations, tests or docs directly; reading, planning and simple commands are fine. `ops-dev` never performs state-changing git operations (pull, merge, push, commit, worktree or branch management); the main agent does those.
